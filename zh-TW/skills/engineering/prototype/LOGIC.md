# 邏輯 Prototype (Logic Prototype)

一個單一、自給自足的 HTML 檔（一個 **shareable demo**（可分享的示範）），讓任何人都能透過點按鈕來操作一個狀態模型。當問題是關於**商業邏輯、狀態轉換或資料形狀**時使用：也就是那種在紙上看起來合理，但只有在你把真實情況推過去之後才會覺得不對勁的東西。

因為它是一個不用安裝任何東西的檔案，你可以把它交給非開發者（設計師、PM、領域專家），讓他們自己去感受這個模型。所以它說的是他們的語言，不是程式碼的語言。

## 什麼時候適合用這個形狀 (When this is the right shape)

- 「我不確定這個狀態機能不能處理先 X 再 Y 的邊界情況。」
- 「這個資料模型真的能讓我表示這樣的情況嗎……」
- 「我想在寫 API 之前，先感受一下它應該長什麼樣子。」
- 任何有人想要**按按鈕並看著狀態改變**的情況。

如果問題是「這個應該長什麼樣子」，這就是錯的分支。請用 [UI.md](UI.md)。

## 流程 (Process)

### 1. 寫出問題 (State the question)

寫程式碼之前，先寫下你要原型化的是什麼狀態模型、什麼問題。一段文字，放在示範的最上方（放在看得見的開頭說明裡，不只是寫在註解裡）。回答錯問題的邏輯 prototype（原型）純粹是浪費，所以要把問題寫明，讓之後可以檢查，不論使用者是現在就在看，還是之後以 AFK（不在場、非同步）的方式回來看。

### 2. 把邏輯隔離在一個可攜的 module 裡 (Isolate the logic in a portable module)

把真正的邏輯（回答問題的那一塊）放在單一個 `<script>` 區塊裡，寫成一個小而純的 module（模組），之後可以整個拿出來放進真正的 codebase（程式碼庫）。它周圍的頁面是拋棄式的；這個 module 不是。

正確的形狀取決於問題：

- **純 reducer**：`(state, action) => state`。適合動作是離散事件、狀態是單一值的情況。
- **狀態機**：明確的狀態和轉換。適合「現在到底哪些動作是合法的」本身就是問題一部分的情況。
- **一小組純函式**，作用在一個普通的資料型別上。適合沒有隱含的目前狀態、只有轉換的情況。
- **一個有一組清楚對外方法的 class 或 module**，適合邏輯真的擁有持續存在的內部狀態的情況。

選最符合所問問題的形狀，*而不是*最容易接到頁面上的那個。保持純粹：沒有 DOM、沒有 `document`、沒有伸進它內部的按鈕 handler。頁面呼叫它；沒有任何東西反方向流動。這就是讓 prototype 在它本身的生命週期結束後仍然有用的原因：一旦問題有了答案，已驗證的 reducer / 狀態機 / 函式組就能直接整個搬進真正的 module。

### 3. 建立可分享的 HTML 檔 (Build the shareable HTML file)

一個檔案，純 HTML/CSS/JS：不用框架、不用 bundler、不用伺服器，全部內嵌，這樣雙擊就能開，用 email 傳來傳去也不會壞。任何人打開它就應該能執行。

為非開發者寫它。每個標籤都用 **domain language**（領域語言：業務本身的用語），不是程式碼用語：按鈕和狀態讀起來要像業務本身，不像 reducer。用白話解釋正在發生什麼。

用清楚的層次排版，由上到下：

1. **標題和一行說明**，說明這個示範讓你探索什麼（第 1 步的那個問題）。
2. **目前狀態**：完整的相關狀態，渲染成一個易讀的面板（有標籤的欄位，不是直接傾印原始 JSON），每次點擊後重新渲染，讓改變看得見。如果有助於非開發者跟上，就把剛剛改變的地方標出來。
3. **自由操作按鈕**：每個動作一個按鈕，隨時可用，讓任何人都能用任意順序戳戳看這個模型。每次點擊都會 dispatch（送出）它的動作，並重新渲染狀態。
4. **引導演練**：一組 **scenarios**（情境），每個分頁一個。每個分頁放一段簡短的白話描述，說明這個 scenario（它設定的情況，以及要注意看什麼），下面是這個 scenario 要依序**按的按鈕**。每一步都是真的按鈕：點了就執行那個動作，並前進到下一步。開始一個演練時會重設到一個已知的初始狀態，讓這個 scenario 每次都以同樣的方式執行。

選能展示棘手情況的 scenario，也就是那些在紙上很難推理的情況：正常路徑、一個棘手的邊界情況、一次嘗試做某件應該不合法的事。

保持美觀但克制：乾淨的字體排版、寬鬆的間距、一個強調色。不要動畫、不要花招：不要任何會跟狀態和按鈕搶注意力的東西。

### 4. 交給對方 (Hand it over)

把檔案傳給他們，或替他們打開。他們有空時會點過演練和自由操作；有趣的時刻是他們說「等等，這應該不可能吧」或「咦，我以為 X 會不一樣」的時候；那些就是*想法*裡的 bug，而這正是重點所在。如果他們想要新的動作或新的 scenario，就加上去。prototype 會演進。

### 5. 保存答案和 prototype (Capture the answer and the prototype)

一旦 prototype 回答了它的問題，就保存答案，然後依照 [SKILL](SKILL.md) 描述的方式保存 prototype。邏輯版本特有的對應方式是：已驗證的 reducer / 狀態機 / 函式組搬進真正的 module（決定被吸收了）；HTML 外殼則跟著進到那個把 prototype 保存為 primary source（第一手資料）的拋棄式 branch（git 分支），而且因為它是一個自給自足的檔案，在那裡仍然可以輕鬆重新執行。

## 反模式 (Anti-patterns)

- **不要加測試。** 需要測試的 prototype 就不再是 prototype 了。
- **不要接到真正的資料庫。** 除非問題明確是關於持久化，否則用記憶體裡的狀態。
- **不要泛化。** 不要有「如果我們之後想支援 X 怎麼辦」。prototype 只回答一個問題。
- **不要把邏輯和頁面混在一起。** 如果純 module 參照了 DOM、`document` 或按鈕 handler，它就不再能被搬出去。讓頁面只是一層包在純 module 外面的薄殼。
- **不要動用框架、bundler 或伺服器。** 一個收件者雙擊就能開的檔案；React app 或 dev server 會毀掉「可分享」這件事。
- **不要把 HTML 外殼上線到正式環境。** 這個頁面是為了讓人手動點過而最佳化的。它背後的邏輯 module 才是值得保留的部分。
