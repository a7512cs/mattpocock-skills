# Diagnosing Bugs

一套處理難搞 bug 的紀律。只有在有明確理由時，才可以跳過階段。

探索 codebase（程式碼庫）時，先讀 `GLOSSARY.md`（如果存在），對相關的 module（模組）建立清楚的心智模型，並檢查你要碰的區域裡的 ADR（架構決策紀錄）。

## 遮蔽機密 (Redact)

這個 skill（技能）會要你展示指令、輸出和擷取到的資料。**先遮蔽每一個機密**：在它的位置寫上 `<REDACTED>`。用環境變數來建立迴圈，讓憑證留在環境裡，而不是出現在你展示的內容中。擷取到的資料會帶有 auth header：只引用帶有訊號的那幾行。

如果遮蔽後的輸出不足以診斷這個 bug，就說出來，並詢問使用者。

## 階段 1：建立回饋迴圈 (Phase 1: Build a feedback loop)

**這一步就是這個 skill 的本體**。其他一切都是機械性的。如果你對這個 bug 有一個**緊密**的 pass/fail 訊號（一個會在*這個* bug 上變紅的訊號），你就會找到原因；二分搜尋、假設驗證和埋點觀測都只是在消耗它。如果你沒有，再怎麼盯著程式碼看也救不了你。

在這裡投入不成比例的心力。**要積極。要有創意。拒絕放棄。**

### 建立迴圈的方法，大致依照這個順序 (Ways to construct one, in roughly this order)

1. 在任何能碰到這個 bug 的 seam（接縫）上寫一個**失敗的測試**：unit、integration、e2e。
2. 對一個執行中的 dev server 跑 **Curl / HTTP script**。
3. 用 fixture（測試固定資料）當輸入做 **CLI 呼叫**，把 stdout 和已知正確的快照做 diff（差異比對）。
4. **Headless browser script**（Playwright / Puppeteer），驅動 UI 並對 DOM/console/network 做斷言。
5. **重播擷取到的 trace**。把真實的網路請求 / payload / event log 存到磁碟；在隔離的狀態下讓它重新跑過那條程式路徑。
6. **用完即丟的 harness**（測試骨架）。啟動系統的一個最小子集（一個服務、mock（模擬）掉的依賴），用單一個函式呼叫就能跑到 bug 的程式路徑。
7. **Property / fuzz 迴圈**。如果 bug 是「有時候輸出錯誤」，就跑 1000 個隨機輸入，找出失敗模式。
8. **Bisection harness**（二分搜尋骨架）。如果 bug 是在兩個已知狀態之間出現的（commit（提交）、資料集、版本），就把「在狀態 X 啟動、檢查、重複」自動化，這樣你就能用 `git bisect run` 跑它。
9. **差異比對迴圈**。把同樣的輸入分別送進舊版和新版（或兩種設定），然後 diff 輸出。
10. **HITL（有人參與的）bash script**。最後手段。如果一定要有人去點，就用 `scripts/hitl-loop.template.sh` 來驅動*他們*，讓迴圈仍然是結構化的。擷取到的輸出會回饋給你。

建立對的回饋迴圈，bug 就修好 90% 了。

### 收緊迴圈 (Tighten the loop)

把迴圈當成一個產品來對待。一旦你有了*一個*迴圈，就把它**收緊**：

- 我能讓它更快嗎？（快取準備工作、跳過不相關的初始化、縮小測試範圍。）
- 我能讓訊號更清楚嗎？（對特定症狀做斷言，而不是「沒有 crash」。）
- 我能讓它更有確定性嗎？（固定時間、設定 RNG seed、隔離檔案系統、凍結網路。）

一個 30 秒、不穩定的迴圈只比沒有迴圈好一點點；一個 2 秒、有確定性的迴圈就是緊密的，是除錯的超能力。

### 非確定性的 bug (Non-deterministic bugs)

目標不是乾淨的重現，而是**更高的重現率**。把觸發動作循環 100 次、平行化、加壓力、縮小時間窗口、插入 sleep。50% 會出現的不穩定 bug 可以除錯；1% 的不行，所以要持續提高重現率，直到可以除錯為止。

### 當你真的無法建立迴圈時 (When you genuinely cannot build a loop)

停下來，明確說出來。列出你試過的方法。向使用者要求：(a) 能重現它的那個環境的存取權，(b) 一份遮蔽過的擷取資料（HAR 檔、log dump、core dump、附時間戳記的螢幕錄影），或 (c) 加入暫時性正式環境觀測點的許可。**不要**在沒有迴圈的情況下就開始提出假設。

### 完成標準：一個會變紅的緊密迴圈 (Completion criterion: a tight loop that goes red)

當迴圈是**緊密的**而且**能變紅**時，階段 1 就完成了：你能說出**一個指令**（一個 script 路徑、一次測試呼叫、一個 curl），而且你**已經至少跑過一次**（展示呼叫方式和它的輸出，要遮蔽過），並且它是：

- [ ] **Red-capable**（能變紅）：它驅動實際的 bug 程式路徑，並對**使用者的確切症狀**做斷言，所以它能在這個 bug 上變紅，修好後變綠。不是「執行時沒出錯」；它必須能*抓到這個特定的 bug*。
- [ ] **Deterministic**（有確定性）：每次執行都得出同樣的判定（不穩定的 bug：依照上面所說，一個固定的、高的重現率）。
- [ ] **Fast**（快速）：以秒計，不是以分鐘計。
- [ ] **Agent-runnable**（agent 可執行）：你可以在無人看管的情況下執行它；人類只能透過 `scripts/hitl-loop.template.sh` 參與迴圈。

如果你發現自己在這個指令存在之前，就在讀程式碼建立理論，**停下來：直接跳到假設，正是這個 skill 要防止的失敗。** 沒有能變紅的指令，就沒有階段 2。

## 階段 2：重現 + 最小化 (Phase 2: Reproduce + minimise)

執行迴圈。看著它在 bug 出現時變紅。

確認：

- [ ] 迴圈產生的是**使用者**描述的失敗模式，而不是剛好在附近的另一個失敗。錯的 bug = 錯的修正。
- [ ] 失敗可以在多次執行中重現（或者，對非確定性的 bug 來說，以足夠高、足以拿來除錯的比率重現）。
- [ ] 你已經擷取到確切的症狀（錯誤訊息、錯誤的輸出、緩慢的時間），讓後面的階段可以驗證修正確實解決了它。

### 最小化 (Minimise)

一旦它變紅了，就把重現情境縮小到**仍然會變紅的最小情境**。**一次一個地**砍掉輸入、呼叫端、設定、資料和步驟，每砍一次就重跑迴圈，只保留對這個失敗來說不可或缺的東西。

為什麼要這麼做：最小的重現情境能縮小階段 3 的假設空間（剩下需要懷疑的活動部件更少），也會變成階段 5 裡乾淨的回歸測試。

當**每個剩下的元素都不可或缺**時就完成了：拿掉其中任何一個，迴圈就會變綠。

在你重現**並且**最小化之前，不要繼續往下。

## 階段 3：提出假設 (Phase 3: Hypothesise)

在測試任何一個假設之前，先產生 **3 到 5 個排好順序的假設**。只產生一個假設，會讓你被第一個看似合理的點子綁住。

每個假設都必須是**可證偽的**：說出它所做的預測。

> 格式：「如果 <X> 是原因，那麼 <改變 Y> 會讓 bug 消失 / <改變 Z> 會讓它更嚴重。」

如果你說不出預測，這個假設就只是一種感覺：丟掉它，或把它磨得更具體。

**在測試之前，先把排好順序的清單給使用者看**。他們常有能立刻重新排序的領域知識（「我們剛部署了一個跟 #3 有關的改動」），或者知道哪些假設他們已經排除過了。便宜的檢查點，省下大量時間。不要卡在這一步；如果使用者 AFK（不在鍵盤前），就照你的排序繼續。

## 階段 4：埋點觀測 (Phase 4: Instrument)

每一個探測都必須對應到階段 3 裡的某個特定預測。**一次只改變一個變數**。

工具偏好：

1. 如果環境支援，用 **Debugger / REPL 檢查**。一個中斷點勝過十條 log。
2. 在能區分各個假設的邊界上放**針對性的 log**。
3. 絕不要「全部都 log 再 grep」。

**每一條 debug log 都加上標籤**，用一個獨特的前綴，例如 `[DEBUG-a4f2]`。最後的清理就變成一次 grep。沒加標籤的 log 會活下來；加了標籤的 log 會被清掉。

**效能分支**。對效能退化來說，log 通常是錯的做法。改成：先建立基準量測（計時 harness、`performance.now()`、profiler、query plan），然後二分搜尋。先量測，再修正。

## 階段 5：修正 + 回歸測試 (Phase 5: Fix + regression test)

在**修正之前**先寫回歸測試，但前提是有一個**正確的 seam** 可以放它。

正確的 seam 是讓測試能跑到呼叫點上實際發生的**真實 bug 模式**的那個 seam。如果唯一可用的 seam 太淺（bug 需要多個呼叫端，測試卻只有單一呼叫端；單元測試無法重現觸發 bug 的那一串呼叫鏈），在那裡寫回歸測試只會給你錯誤的信心。

**如果不存在正確的 seam，這件事本身就是發現**。記下來。codebase 的架構阻止了這個 bug 被鎖住。把這點標記給下一個階段。

如果存在正確的 seam：

1. 把最小化後的重現情境變成那個 seam 上的一個失敗測試。
2. 看著它失敗。如果你是透過修改程式碼或 fixture 來強迫它變紅的，就拿它跟一份原始乾淨的副本做 `diff`，在相信它之前先證明那個修改確實生效了。
3. 套用修正。
4. 看著它通過。
5. 針對原始的（未最小化的）情境，重跑階段 1 的回饋迴圈。

## 階段 6：清理 (Phase 6: Cleanup)

宣告完成之前必須做到：

- [ ] 原本的重現情境不再重現（重跑階段 1 的迴圈）
- [ ] 回歸測試通過（或已記錄沒有 seam 這件事）
- [ ] 所有 `[DEBUG-...]` 觀測程式碼都已移除（`grep` 那個前綴）
- [ ] 用完即丟的 prototype（原型）已刪除（或移到明確標示的 debug 位置）
- [ ] 最後證實正確的假設寫在 commit / PR（pull request）訊息裡，讓下一個除錯的人能學到
