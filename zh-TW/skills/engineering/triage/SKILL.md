# Triage

讓專案 Issue tracker（議題追蹤系統）上的 Issue 走過一個由 triage（分類處理）role 構成的小型狀態機。

如果這個 repo（程式碼倉庫）把外部 pull request 當作請求入口（見 issue-tracker 設定），triage 也涵蓋它們：**PR 就是附帶程式碼的 Issue**，使用同樣的 role、同樣的狀態、同樣的狀態機，只有少數差異，在下面以「針對 PR」(for a PR) 標示。依照 tracker 設定，把單獨的 `#42` 解析為 Issue 或 PR。

triage 期間發布到 Issue tracker 的每一則留言或每一個 Issue，都**必須**以這段免責聲明開頭：

```
> *This was generated by AI during triage.*
```

## 參考文件 (Reference docs)

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何寫出經得起時間考驗的 agent brief（給 agent 的任務說明）
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知識庫如何運作

## 角色 (Roles)

兩個 **category**（類別）role：

- `bug`：某個東西壞了
- `enhancement`：新功能或改進

五個 **state**（狀態）role：

- `needs-triage`：維護者需要評估
- `needs-info`：等待回報者提供更多資訊
- `ready-for-agent`：規格已完整，可以交給 AFK（不在場、非同步執行的）agent
- `ready-for-human`：需要人工實作
- `wontfix`：不會處理

針對 PR，同樣的狀態是對照附帶的程式碼來解讀：`ready-for-agent` 表示已經附上 brief，而且 agent 應該針對 diff（差異內容）採取下一步；`ready-for-human` 表示它已經可以讓人類 merge（合併）了。

每個 triage 過的 Issue 都應該剛好帶有一個 category role 和一個 state role。如果 state role 互相衝突，就標出來，並在做任何其他事之前先問維護者。

這些是標準的 role 名稱。Issue tracker 中實際使用的 label 字串可能不同。對照表應該已經提供給你了。如果沒有，告訴使用者執行 `/setup-matt-pocock-skills`。

狀態轉換：沒有 label 的 Issue 通常先進到 `needs-triage`；從那裡再移到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦回報者回覆，`needs-info` 就回到 `needs-triage`。維護者隨時可以覆寫；看起來不尋常的轉換要標出來，並在繼續之前先詢問。

## 呼叫方式 (Invocation)

維護者呼叫 `/triage`，並用自然語言描述他們想要什麼。解讀這個請求並採取行動。範例：

- 「給我看任何需要我注意的東西」
- 「我們來看看 #42」（Issue 或 PR）
- 「把 #42 移到 ready-for-agent」
- 「有哪些已經準備好讓 agent 接手了？」

## 顯示需要注意的項目 (Show what needs attention)

查詢 Issue tracker，並呈現三個分組，最舊的在前：

1. **沒有 label (Unlabeled)**：從來沒被 triage 過。
2. **`needs-triage`**：評估進行中。
3. **自上次 triage 筆記以來回報者有新動態的 `needs-info`**：需要重新評估。

當 PR 在範圍內時，把外部 PR 也放進這些分組，並在每一行標上 `[PR]` 或 `[issue]`。搜尋發現階段只會找出*外部* PR（tracker 設定定義誰算外部），所以協作者正在進行中的 PR 不是 triage 的工作。這個篩選只用在搜尋發現階段；被明確點名的 PR 不論作者是誰，一律會被 triage。

顯示數量，以及每個項目一行摘要。讓維護者挑選。

## Triage 一個特定的 Issue 或 PR (Triage a specific issue or PR)

1. **蒐集 context（上下文）。** 讀完整的 Issue 或 PR（內容、留言、label、作者、日期；針對 PR，也要讀 diff）。解析任何先前的 triage 筆記，這樣你就不會重問已經解決的問題。使用專案的領域 glossary（詞彙表）探索 codebase（程式碼庫），並尊重該區域中的 ADR（架構決策紀錄）。對 codebase 做兩項檢查：(a) **redundancy**（重複）：依領域概念（不只是請求的措辭）搜尋所請求行為的現有實作，並回報你找過哪些地方。如果找到了，它就是一個「已經實作」的 `wontfix`（第 5 步）。(b) **prior rejection**（先前被拒絕過）：讀 `.out-of-scope/*.md`，並提出任何跟這個請求相似的項目。

2. **提出建議。** 告訴維護者你建議的 category 和 state，附上理由，再加上一段跟這個請求相關的簡短 codebase 摘要（包括它是否已經實作了）。等待指示。

3. **驗證說法。** 在任何 grilling 之前，先檢查這個說法站不站得住腳。針對 bug，依照回報者的步驟重現它。針對 PR，確認 diff 做到了它宣稱的事：把它 check out 下來，執行相關的測試或指令。回報發生了什麼：已確認（附上程式碼路徑）、失敗，或細節不足（一個強烈的 `needs-info` 訊號）。經過確認的驗證會讓 agent brief 有力得多。

4. **Grill（如果需要）。** 如果這個請求需要補充細節，就呼叫 Skill 工具兩次，分別用 "grilling" 和 "domain-modeling"，一次一輪問題地把它追問到成形，在決定確定時就地精煉領域術語，並更新 `GLOSSARY.md`/ADR。

5. **套用結果：**
   - `ready-for-agent`：發布一則 agent brief 留言（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：結構跟 agent brief 一樣，但要註明為什麼它不能委派出去（判斷題、需要外部存取、設計決定、手動測試）。
   - `needs-info`：發布 triage 筆記（範本見下方）。
   - 針對 `wontfix`，關閉 Issue，留言內容取決於*為什麼*：
     - **已經實作 (Already implemented)**：這個改變已經存在於 codebase 中。指出它在哪裡；**不要**寫進 `.out-of-scope/`（那個知識庫是給*被拒絕*的請求用的，不是給已經做好的）。
     - **被拒絕（bug） (Rejected (bug))**：給一個禮貌的解釋，然後關閉。
     - **被拒絕（enhancement） (Rejected (enhancement))**：寫進 `.out-of-scope/`，從一則留言連結到它，然後關閉（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：套用這個 role。如果有部分進展，可以選擇性留言。

## 快速覆寫狀態 (Quick state override)

如果維護者說「把 #42 移到 ready-for-agent」，就信任他們，直接套用這個 role。確認你接下來要做什麼（role 變更、留言、關閉），然後行動。跳過 grilling。如果在沒有 grilling session（工作階段）的情況下移到 `ready-for-agent`，就問他們是否要寫一份 agent brief。

## Needs-info 範本 (Needs-info template)

```markdown
## Triage 筆記 (Triage Notes)

**目前為止已確認的事項 (What we've established so far)：**

- 重點 1
- 重點 2

**我們還需要你 (@reporter) 提供的：**

- 問題 1
- 問題 2
```

把 grilling 期間解決的所有事項都記在「目前為止已確認的事項」(established so far) 底下，這樣工作才不會遺失。問題必須具體、可以採取行動，而不是 "please provide more info"（請提供更多資訊）。

## 接續先前的 session (Resuming a previous session)

如果這個 Issue 或 PR 上已經有先前的 triage 筆記，就讀它們，檢查回報者是否已經回答了任何尚未解決的問題，並在繼續之前呈現一份更新後的全貌。不要重問已經解決的問題。
